# 1食ずつの食事記録（per-meal logging）設計

- 日付: 2026-09-03
- 対象: `diet-tracker-pwa.html`（単一ファイルPWA）
- 版: APP_VERSION 2.0 → 3.0（保存形式の破壊的変更を伴うため major を上げる）

## 背景と目的

現在の保存形式は「1日1件のログに合計カロリー・合計タンパク質を数値で1つずつ持つ」もので、
何をどれだけ食べたかは残らない。またレシピ154品は `kcal`・`protein` を持っているのに記録側と
つながっておらず、利用者はレシピの数値を見てから記録フォームへ手で転記している。

本変更で、食事を1食ずつ記録できるようにし、レシピからワンタップで記録へ反映できるようにする。

## 決定事項（合意済み）

1. **1食単位に一本化する。** 1日の合計は各食の合計から都度算出し、合計値は保存しない。
   合計を直接入力する欄は廃止する（内訳と合計が食い違う状態を作らないため）。
2. **レシピに無い食事は手入力し、「よく食べるもの」として保存する。** 同名は使用回数を加算し、
   次回からは1タップで追加できる。
3. 食事帯は **朝食 / 昼食 / 夕食 / 間食 / その他** の5つ。

## データモデル

### v2 形式

```js
{
  schemaVersion: 2,
  logs: [
    {
      date: "YYYY-MM-DD",
      weight: 72.4,        // 任意（食事だけ記録した日は持たない）
      trained: false,
      meals: [
        { id: "m_1735...", time: "breakfast", name: "鶏むね肉と卵の和風そぼろ丼",
          kcal: 420, protein: 45, source: "recipe" }
      ]
    }
  ],
  foods: [
    { id: "f_1735...", name: "コンビニのサラダチキン", kcal: 110, protein: 25,
      useCount: 12, lastUsedAt: "2026-09-03T12:10:00.000Z" }
  ],
  profile: { startWeight, goalWeight, targetCalories?, targetProtein? }  // 変更なし
}
```

- `time`: `"breakfast" | "lunch" | "dinner" | "snack" | "other"`
- `source`: `"recipe" | "manual" | "food" | "migrated"`（由来の記録。表示には使わないが移行分の識別に使う）
- `protein` は任意（不明な食事があるため）。合計時は未指定を 0 として扱うが、値を捏造して保存しない。
- `weight` が**任意になる**のが v1 からの最大の差分。
- `id` は `"m_" + Date.now() + "_" + カウンタ`（`foods` は `"f_"` 接頭辞）で生成する。同一ミリ秒での
  重複を避けるためカウンタを併用する。id は表示せず、削除・取り消しの対象特定にのみ使う。

### 食事帯の定数

既存の `MEAL_TIME_LABEL`（朝食/昼食/夕食）と `MEAL_TIME_ORDER`（3件）は**レシピ表示が参照している**ため
変更しない。記録用に別の定数を追加する:

```js
var LOG_MEAL_TIME_LABEL = { breakfast: "朝食", lunch: "昼食", dinner: "夕食", snack: "間食", other: "その他" };
var LOG_MEAL_TIME_ORDER = ["breakfast", "lunch", "dinner", "snack", "other"];
```

## 移行（v1 → v2）

`loadState()` 内で、読み込んだデータに `schemaVersion` が無い場合のみ実行する。

1. **移行前の生データを退避する。** `localStorage["nexra-diet-tracker-backup-v1"]` へ、パース前の文字列を
   そのまま1回だけ保存する。すでにキーが存在する場合は上書きしない（最初の退避を最優先で守る）。
2. 各ログを変換する:
   - `calories` または `protein` が数値の日 → `meals: [{ time: "other", name: "まとめて記録（移行）",
     kcal: <calories or 0>, protein: <protein があれば設定>, source: "migrated" }]`
   - どちらも無い日 → `meals: []`
   - `weight`・`trained` は変更しない。`calories`・`protein` はログ直下から削除する。
3. `foods: []` を初期化し、`schemaVersion: 2` を設定して保存する。

**合計値は移行の前後で変化しない**ことを不変条件とする。移行は冪等で、`schemaVersion` があるデータには
一切手を触れない。

## 算出（保存しない値）

```js
dayKcal(log)    = log.meals.reduce((s, m) => s + (m.kcal || 0), 0)
dayProtein(log) = log.meals.reduce((s, m) => s + (m.protein || 0), 0)
```

`meals` が空の日は「未記録」として扱い、0 と区別する（ゲージに 0/1500 と出さない）。

## UI

### 記録タブ

- **本日の摂取**: ゲージ（kcal・タンパク質の対目標）＋ 食事帯ごとの一覧。各行に名前・kcal・P・削除ボタン。
  食事が無い帯は「（未記録）」を淡色で表示。`other` 帯は中身がある時だけ表示する。
- **食事を追加**（新設）:
  - 食事帯セレクタ。既定値は現在時刻から決める（〜10:30 朝食 / 〜15:00 昼食 / 〜21:00 夕食 / それ以外 間食）。
  - 日付（既定は今日。前日の記録を後から足せるようにする）。
  - 「よく食べるもの」チップ（`useCount` 降順・同数なら `lastUsedAt` 降順、上位12件）。タップで即追加。
  - 手入力: 名前（必須）・kcal（必須・正の整数）・タンパク質（任意・0以上の整数）。
    追加時に `foods` へ upsert（同名・大文字小文字と前後空白を無視して比較。`useCount` を加算し
    `kcal`・`protein` は最新の入力で更新）。
- **「記録を追加」を「体重を記録」へ改称**: 体重とジムのみ。kcal・タンパク質の入力欄と、
  `addOrUpdateLog()` のそれらの引数を撤去する。
- **`addOrUpdateLog()` を「差し替え」から「マージ」へ変える（重要）。** 現在の実装は
  `state.logs[idx] = entry` でエントリを丸ごと置き換えており、v1 では「朝に体重＋カロリーを記録し、
  夜に体重だけ記録するとカロリーが消える」不具合として現れていた。v2 では同じ経路が
  **その日の `meals` を丸ごと消す**ため致命的になる。既存エントリに `weight`・`trained` だけを
  上書きし、`meals` を保持する形へ変更する。
- **履歴**: 体重が無い日は `—` を表示（`fmt1(l.weight)` の無条件呼び出しをやめる）。
  行をタップでその日の食事内訳を開閉する。
- **削除の確認**: 1食の削除は確認ダイアログを出さない（押し間違えても再追加が軽い操作のため）。
  1日分をまとめて消す既存の履歴削除は、従来どおり確認を出す。トーストの表示は約5秒、
  その間だけ「取り消し」を押せる。
- 目標設定・データ管理は変更しない。

### 食事例タブ

各レシピカードと詳細モーダルに「記録に追加」を置く。押下で食事帯（時刻から自動選択、変更可）を
確認して追加し、`「+420kcal / P45g を記録しました ｜ 取り消し」` のトーストを出す。
取り消しは追加した食事の `id` を消すだけで、他の記録には影響しない。

### 推移タブ

`metricLogs("calories" | "protein")` を `meals` からの算出値に変更する。`meals` が空の日は点を打たない。
体重の系列は変更しない（体重が無い日は従来どおり除外される）。

## インポート / エクスポート

- **エクスポート**: v2 形式（`schemaVersion: 2`・`foods` を含む）で書き出す。
- **インポート**: v1 と v2 の両方を受理する。`schemaVersion` が無い場合は上記の移行を通してから取り込む
  （手元に残っている古いバックアップを読めなくしないため）。
- **`validateImportedData()` の修正**:
  - `weight` を**任意**にする（存在する場合のみ数値であることを検証）。これを直さないと、
    体重の無い日を含むバックアップが復元できない。
  - `meals` が存在する場合、配列であり各要素の `time` が既知の値、`name` が文字列、
    `kcal` が数値、`protein` が未指定または数値であることを検証する。
  - `foods` が存在する場合、配列であり各要素の `name` が文字列、`kcal`・`protein` が数値であることを検証する。

## 検証

テスト基盤が無いリポジトリだが、実データの移行を含むため目視確認だけでは不足と判断した。
単一ファイル構成を壊さない方法として、`?selftest=1` で開いたときにページ内でアサーションを実行し
結果を一覧表示するモードを追加する。

対象:

1. 移行: カロリーのみの日 / タンパク質も持つ日 / どちらも無い日 / 空の `logs` / すでに v2 のデータ（不変）
2. 移行の冪等性: 2回通しても結果が変わらない
3. 移行の不変条件: 合計 kcal・合計 P が移行前後で一致
4. 退避キー: 既存の退避があれば上書きしない
5. 算出: `dayKcal`・`dayProtein`、`meals` が空の日と 0 の日の区別
6. インポート検証: v1 を受理 / v2 を受理 / 体重なしを受理 / 不正な `meals` を拒否
7. `foods` の upsert: 同名の統合・`useCount` 加算・前後空白の無視
8. `addOrUpdateLog()` のマージ: 食事が入っている日に体重だけ記録しても `meals` が消えない

そのうえで Chrome で実操作を確認する（レシピから追加 → ゲージ反映 → 取り消し → 履歴が落ちない →
エクスポートしたJSONを再インポートできる）。最後にコミット・push し、GitHub Actions のデプロイ成功と
本番URLの200を確認する。

## リスクと対応

| リスク | 対応 |
|---|---|
| 移行バグで実データ（数か月分）が壊れる | 移行前の生データを別キーへ退避。加えて利用者が事前にエクスポートで端末外へ控えを取る |
| 体重が任意になったことで別の箇所が落ちる | `l.weight` を直接使う箇所を全数 grep して確認する（既知は `renderHistory`・`validateImportedData`） |
| 古いバックアップが読めなくなる | インポートで v1 形式を受理する |

## オーナー作業

- 新しい版をスマホで開く**前に**、現行版でエクスポートしてバックアップを取る。

## やらないこと

- レシピ集そのものへのユーザー追加（献立提案と食事記録が混ざるため。「よく食べるもの」で代替する）
- 食事の写真、外部の食品データベース連携、通知
