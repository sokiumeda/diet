# バーコード読み取りによるカロリー取得 設計

- 日付: 2026-09-03
- 対象: `diet-tracker-pwa.html` ＋ 同梱するバーコード読み取りライブラリ ＋ `sw.js`
- 版: APP_VERSION 3.0 → 3.1。**`sw.js` の `CACHE_NAME` は v7 → v8**（precache する
  ファイルが増えるため。上げ忘れると `activate` が旧キャッシュを消さず、ライブラリを持たない
  古いHTMLが配られ続けて読み取りが無言で動かない）
- 前提: [[2026-09-03-per-meal-logging-design.md]] で導入した v2 スキーマ（1食ずつの記録）

## 背景と目的

食事の記録で一番面倒なのはカロリーを調べて手で打つこと。市販品はバーコードを読めば
栄養情報を引けるため、その導線を作る。記録される食事は既存の `meals` 配列にそのまま入り、
`source: "barcode"` が増えるだけなので、保存形式の変更は伴わない。

## 実現性（2026-09-03 実測）

- データ源は **Open Food Facts**。無料・APIキー不要・アカウント開設不要（新たな費用は発生しない）。
- 実在JANコード15件（うち7件はOFFと無関係な独立の商品ページから収集）で **ヒット14件**、
  ヒットした14件は **全件カロリーあり**。
- GitHub Pages の origin から直接呼べる（`access-control-allow-origin: *` を実測確認）。
- レート制限は商品取得API 15req/min/IP。個人利用では当たらない。
- **`BarcodeDetector` は iOS Safari が非対応**（実装はあるがフラグの裏で無効）。よって
  カメラ映像＋JSライブラリでのデコードが必要。

## 決定事項（合意済み）

1. **ライブラリを同梱してカメラで読み取る。** `@zxing/library` **0.23.0**（純JS・UMD・Apache-2.0）を
   **バージョンを固定して** `vendor/` 配下に置き、**LICENSE / NOTICE も同梱する**（Apache-2.0の要件）。
   UMD版の実寸は **362KB（未圧縮）／gzip後 107KB**（実測）。
   `sw.js` の `PRECACHE_URLS` に追加する。**CDN読み込みは採らない** — 現在の「オフラインで
   起動できる」性質が CDN 障害や圏外で壊れるため。wasm版は高速だが1MB級なので採らない。
   単一HTMLファイルという性質は失われる（これは承知のうえでの選択）。
   - **既知の非推奨**: 公式はカメラ関連APIを `@zxing/browser` へ移行推奨中で、`@zxing/library`
     単体でのブラウザ利用は非推奨方向にある。ただし現行0.23.0のUMDにブラウザ用カメラAPIは
     同梱されており動作は妨げられていない。**まず1パッケージで済む `@zxing/library` で進め、
     デコードが実機で動かない／将来削除された場合に `@zxing/browser` へ移す**。この判断を
     ここに記録するのは、後から見た人が「なぜ非推奨の方を使ったのか」を調べ直さずに済むため。
2. **読み取り後は確認画面を出す。** 商品名・分量・算出値をすべて編集可能にしてから記録する。
3. **失敗したら必ず手入力へ逃がす。** 「読めなかったので諦める」導線は作らない。

## 分量の換算（この機能の核心）

OFF が返すのは **100gあたり**の値であり、1袋のカロリーではない。実測例:

| JAN | 商品 | kcal/100g | serving_quantity | product_quantity |
|---|---|---|---|---|
| 4901940200641 | ファミマル なげわ | 547.8 | 67 | 67 |
| 4901005009158 | ポッキー | 489.7 | 29 | (なし) |
| 4909411076610 | 午後の紅茶 500ml | 15 | (なし) | 500 |

**既定の分量はこの順で決める:**

1. `serving_quantity` があればそれ（1食分）
2. 無ければ `product_quantity`（1包装ぶん）
3. どちらも無ければ空欄にして利用者に入力させる

**算出式**: `値 = 100gあたりの値 × 分量 ÷ 100`。
検算: なげわ 67 × 547.8/100 = 367 で、OFF自身の `energy-kcal_serving`(367) と一致する。

**分量を変えると kcal とタンパク質が即座に再計算される。** 半分残した・2袋食べた、を自然に扱うため。

**単位は g / ml を出し分ける。** `quantity` 文字列（"500 ml" 等）から ml を判定し、
判定できなければ g とする。換算式は単位によらず同じ。

## 商品名は編集可能にする（必須）

OFF の商品名は品質が低い。実測で確認した実例:

- ポッキー → `Pocky chocolate`（英語のみ、`product_name_ja` も同じ英語）
- 午後の紅茶 → `Gogo no kocha Straight Tea`（ローマ字）
- ファミマル なげわ → `product_name_ja` が **「やげわ」と誤登録**されている

そのまま記録すると履歴に読みにくい名前・誤った名前が並ぶため、確認画面で名前を編集できることは
任意ではなく要件とする。表示の優先順は `product_name_ja` → `product_name` → JANコード。

## 画面の流れ

```
[食事を追加] 内の「バーコードを読み取る」
      ↓ カメラ起動（getUserMedia・背面カメラ優先）
      ↓ JAN検出 → 即カメラ停止（電池とプライバシーのため映像を持ち続けない）
      ↓ OFF照会 api/v2/product/{jan}.json?app_name=…&fields=…
      ↓
   ┌─ ヒット → 確認画面 → 記録
   └─ 失敗   → 手入力フォームへ（分かる範囲だけ埋める）
```

### 確認画面の項目

- 商品名（編集可・初期値は上記の優先順）
- 100gあたりの表示（読み取った生の値。編集不可・根拠として見せる）
- 分量（編集可・既定値は上記の優先順・単位付き）
- 算出された kcal / タンパク質（分量に連動して再計算・**手で上書きも可**）
  - **上書きと再計算の優先順を明確にする**: 利用者が kcal を手で書き換えたら、その値を
    「上書き済み」として保持し、以後その画面では分量を変えても**自動再計算しない**
    （黙って書き換えると、直した値が消えて混乱するため）。分量の変更で再計算を再開したい
    場合に備え、上書き中はその旨を示し、リセットできるようにする。kcal と タンパク質は
    それぞれ独立に上書き状態を持つ
- 食事帯（既定値は時刻から。`defaultMealTime` を再利用）
- 日付（既定は今日）
- **出典表示**（後述・常時表示）
- [記録に追加] / [やめる]

記録される食事は既存の `addMeal(date, time, name, kcal, protein, source)` を通し、
`source: "barcode"` を渡す。**JANコードは食事オブジェクトに保存しない**（表示にも検索にも
使わないため。必要になった時点で足す）。

確認して記録したものは `upsertFood` で「よく食べるもの」へ登録する。常食は2回目以降
スキャン不要で1タップになる。

## 失敗時の扱い

| 失敗 | 対応 |
|---|---|
| カメラ権限が拒否・カメラ無し | JANコードの手入力欄を出す（打てば同じ照会が走る） |
| 一定時間読み取れない | 同上 |
| 商品が未収載（実測で約7%） | 手入力フォームへ。読み取れたJANを画面に残す |
| kcal が未登録 | 商品名だけ埋め、kcal は空欄で確認画面を出す |
| 通信失敗・オフライン | 手入力フォームへ。読み取れたJANを画面に残す |
| protein だけ無い | **空欄のまま**。0を捏造しない（v2スキーマの既存方針） |
| レート制限超過（15req/min 超過・429等） | 通信失敗と区別し「時間をおいて再試行」と伝えて手入力へ。自動リトライはしない |
| EAN-13 以外を読んだ（UPC-A等の海外商品） | 読めた数字でそのまま照会する（OFFはUPCも収録）。外れれば通常の未収載扱い |

自動リトライは実装しない（レート制限を無駄に消費するため）。

## 法的義務・制約

- **出典表示は ODbL 上の義務**であり任意の配慮ではない。**社名の表示だけでは足りない。**
  データベース由来であることとライセンス名(ODbL)の明示、およびライセンスへのリンクが要る。
  確認画面に次の3点を常時表示する:
  1. この情報が Open Food Facts のデータベース由来であること
  2. **Open Database License (ODbL) の下で提供されている**旨と、ライセンスへのリンク
     ( https://opendatacommons.org/licenses/odbl/ )
  3. その商品のページへのリンク ( https://world.openfoodfacts.org/product/{JAN} )
  文面は OFF 公式の推奨表現に沿わせる。**「Open Food Facts」の社名表示だけで済ませない。**
- **User-Agent 要件は満たせない。** OFF は独自 User-Agent を求めているが、ブラウザの `fetch`
  では User-Agent は禁止ヘッダで設定できない。代替として `app_name` / `app_version` を
  クエリで渡す（HTTP 200 を実測確認）。**「UA要件に対応済み」と書いてはならない** — 満たせて
  いないという事実をここに残す。
- **プライバシー**: 読み取ったJANコードが第三者（Open Food Facts）へ送信される。このアプリで
  初めて端末外へデータが出る機能なので、確認画面と設定まわりに明示する。
  体重・食事記録そのものは一切送信しない。

## テスト

`?selftest=1` の既存ハーネスに追加する。**純粋関数に切り出してテストする:**

1. `parseOffProduct(json)` → `{name, kcalPer100, proteinPer100, defaultQty, unit, productUrl}`
   `productUrl` は `https://world.openfoodfacts.org/product/{JAN}`（出典リンク先）。
   固定データには**上で実測した3商品の実レスポンス**をそのまま使う。
   - serving あり（なげわ・ポッキー）→ `defaultQty` は serving_quantity
   - serving なし・quantity あり（午後の紅茶）→ `defaultQty` は product_quantity
   - どちらも無い → `defaultQty` は未定義
   - `product_name_ja` → `product_name` → JAN の優先順
   - ml 判定（"500 ml" → unit "ml"、"67g" → unit "g"）
   - kcal が無い商品 → `kcalPer100` は未定義（0にしない）
   - protein が無い → `proteinPer100` は未定義（0にしない）
2. `computeFromPer100(per100, qty)` → 四捨五入した整数。`per100` が未定義なら未定義を返す。
3. `status: 0`（未収載）と不正JSONで例外にならないこと。

カメラと実通信はテストで叩かない。

**実機デコードは未検証の前提であり、ゲートとして扱う。** `@zxing/library` が iOS Safari の
`getUserMedia` 映像から EAN-13 を実際にデコードできるかは、ライブラリ内にAPIが存在することしか
確認できていない。したがって実装は**最初に読み取り単体の動作確認を通す**構成とし、
デスクトップChromeで通ったうえで、**オーナーにiPhoneでの読み取り確認を依頼する**。
ここが通らなければ `@zxing/browser` かwasm版への切り替えを検討し、それでも駄目なら
JANコード手入力版に縮退する（照会の価値は残る）。

## リスクと対応

| リスク | 対応 |
|---|---|
| ライブラリ同梱で単一ファイルでなくなる | 承知のうえの選択。`sw.js` に登録してオフライン起動は維持する |
| iOS PWA のカメラ権限の摩擦（起動ごとに許可を求められる報告あり） | ブロッカーではない。拒否時は手入力へ逃がす |
| OFF の商品名が英語・ローマ字・誤記 | 名前を編集可能にする（要件） |
| 100gあたりの値をそのまま記録してしまう | 確認画面で必ず分量を経由させる。素通りする導線を作らない |
| ネットワーク必須の機能が初めて入る | オフライン時は読み取りまで動かし、手入力へ誘導する |

## やらないこと

- 栄養情報の端末内キャッシュ（同じ商品を繰り返し引く場合は「よく食べるもの」で足りる）
- OFF への商品情報の投稿・修正（書き込みはアカウントが要る。オーナー専任領域）
- バーコード以外の読み取り（レシートOCR・料理写真の推定など）
- wasm版デコーダへの移行（純JS版で実用に足りなければ再検討する）
